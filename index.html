项目档案

AI APPLICATION · 2026.09—NOW◉

AI 友人

独立构建具备长期记忆与主动对话能力的 AI 应用，围绕主动性、消息打扰控制和调用成本持续迭代。

  • 20+ 组场景测试，主动开口率从不足 20% 提升至 89%
  • 设计静默时段、每日上限、连续发送上限、冷却期四层机制
  • 落地 Token 成本账本；27 项测试验证零回归
  • 真机测试并推动修复 10+ 项问题

KEY DECISIONS & TRADE-OFFS

  • 规则定边界、模型做决策：静默时段、每日上限、连续发送上限、冷却期四条硬约束不交给模型，只让它在边界内判断"这次开口值不值得"，避免为了指标牺牲"不打扰"。
  • 放弃的方案：最早想让模型自主决定所有触发时机，结果打扰不可控、命中率也不到 20%；改成两段式后场景测试命中率才升到 89%。
  • 回头看不够：四层参数是手工调参，没有线上 A/B；89% 是自建用例口径，样本量小。

PYTHON + MYSQL · 2026.06▦

网吧管理系统

从需求分析到数据库建模与业务查询，完成一个面向网吧日常业务的管理系统。

  • 基于 Python + MySQL 完成系统开发
  • 设计 8 张业务数据表并完成 ER 建模
  • 使用 SQL 实现会员消费排行、商品销量统计、充值流水核对

KEY DECISIONS & TRADE-OFFS

  • 先把表设计对，再写业务：先完成会员、商品、充值、消费流水等 8 张表的 ER 建模与关系设计，再落业务逻辑，避免边写边改表。
  • 统计留在 SQL 里：消费排行、销量统计、流水核对都用多表查询直接完成，不把数据拉到应用层再算——这正是数据类岗位的日常动作。
  • 回头看不够：只覆盖了课程范围内的核心链路，退款、重复充值、并发下余额一致性这类异常场景没有处理。
↗ github.com/WAW689/NetCafe-Management-System
MINI PROGRAM · 2026.01—03◇

勋章待办

微信小程序产品设计与 AI 辅助开发，以游戏化机制帮助用户管理任务并形成持续反馈。

  • 独立完成需求分析与 PRD
  • 覆盖任务管理、勋章激励、多人协作、标签管理
  • 设计动态勋章稀有度机制
  • 产品上线并完成首批真实用户验证

KEY DECISIONS & TRADE-OFFS

  • 先定激励，再定界面：先把"完成任务之后用户得到什么"写进 PRD，再画任务列表与勋章体系，保证反馈闭环成立。
  • 用稀有度替代固定徽章：动态稀有度让长期坚持有递进感，而不是做完一次就结束。
  • 放弃的方案：没有做排行榜和社交玩法——冷启动阶段人少，反而会放大"没人用"的观感。
  • 回头看不够：首批真实用户只有两位数，稀有度参数缺少样本支撑，流失原因也没有系统收集。

局限与反思

SELF-AUDIT · 我知道自己的边界
  • 89% 主动开口率是自建口径：来自 20 多组人为构造的场景用例，不是线上大样本统计。要用线上数据验证，需要补主动消息回复率、次日留存、打扰投诉率三个指标。
  • Token 成本账本没有对账：账本口径是我自己定义的调用归类，没有和平台账单做过交叉验证，只能用于内部功能取舍，不能当财务报表用。
  • 27 项测试是自建安全网：项目全程单人开发、没有代码评审，测试覆盖的是我能预想到的边界；预想不到的地方，测试同样挡不住。
  • RAG 只有概念理解：没有在生产项目里落地过，LangChain / LlamaIndex / 向量数据库都还没实操，这也是我目前在补的部分。
  • 小程序用户量很小：累计两位数（首批 11 位）。它验证的是"需求 → PRD → 上线 → 真实反馈 → 迭代"的闭环，不是增长能力。
  • 网吧管理系统是课程项目：它证明的是数据基本功（ER 建模、多表查询、统计），不代表工程规模经验。

把这些放在页面上，而不是只留在简历之外，是因为面试里被追问时，我更希望答案由我自己先说出来——知道边界在哪，才知道下一步该补什么。
